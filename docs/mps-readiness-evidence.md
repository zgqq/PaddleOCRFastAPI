# Isolated MPS clean-install and Docker CPU boundary

This records **candidate acceptance only**, not permission to deploy. Persistent `macos-ppocr-v6` remains at `e6b04cb`; implementation branch `impl/20261004-paddle-mps-readiness` starts at that exact commit. The target Mac was resolved via Resource Manager `ai.service.rapidocr-mps` → `home.machine.claw-gateway-macmini`, and the authorized SSH access path was obtained through `resource_manager.access.get`. No production package, source, listener, launchd unit, symlink or route was changed.

The original Bullseye Dockerfile with hardcoded Tsinghua Debian mirror failed at `apt-get install` (security package URLs 404). The candidate uses the Python 3.9 Bookworm base and default Debian/PyPI sources instead. The default Paddle CPU pin set remains in `requirements.txt`; the optional MPS pin set remains in `requirements-mps.txt`. The Docker CPU inference failure was a *real HTTP 500*, while `/ready` had already returned 200; the Linux-only `enable_mkldnn=False` fix was verified with real inference, not inferred from readiness.

Scope limits: no production restart/switch, no production inference acceptance, no individual MPS-kernel tracing or long-duration load testing. `/ready` only checks the three model parameter devices. The candidate remains a non-deployable experiment until a separate release review and explicit authorization.
